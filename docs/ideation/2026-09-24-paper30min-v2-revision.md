# Paper30Min v2.0.0 方向修订：把现有阅读链路接起来

本修订承接 [初版方向报告](2026-09-24-paper30min-v2-ideation.html)。使用者明确提出：v2.0.0 应优先调整、升级和重构现有能力，而不是扩充功能；还希望从 v2.0.0 起支持应用内更新，并为未来移动端和云服务做好数据边界准备。以下排序据此取代初版报告中的六项候选排序；它是产品与架构建议，不是已确认的开发计划。

## 现状核对

| 关注点 | 当前实现 | 对 v2.0.0 的含义 |
| --- | --- | --- |
| 代码品质 | `app/ui/js/main.js` 同时处理阅读视图、地图、原文、翻译、问答和 PDF；`app/ui/js/view.js`、`qa.js` 等已提取纯逻辑，Rust 侧也已有协议和 PDF 映射模块。不能仅凭文件长度断言代码质量差，但阅读状态在 `reader` 与 `sourceTab`、`pdfPage`、`pdfSidebarOpen` 等局部变量之间同步，跨模块改动成本值得审查。 | 先做针对性的耦合审查，找出重复状态、跨层调用和难以测试的渲染逻辑；按边界分批简化。 |
| 阅读方式 | 地图、原文、提问、回想卡是顶层 tab；地图内还有节页。地图和原文共用节树，但切换后是两套阅读表面。译文按节或全文保存，显示在原文视图的独立对照区。 | 以“当前论文、当前章节、当前证据位置”为统一阅读上下文，重排页面。 |
| 提问 | `qa.js` 会注入 L1、当前绑定的 L2/原文或全文，并重放最近 12 条消息；论文最多保留最近 40 条问答。因此已经支持基本多轮上下文。问答提示词明确禁止取证工具，发送链路每轮调用一次 `model.chat`。 | 升级重点是按需取证、上下文压缩和工具轨迹，而不是从零添加聊天历史。 |
| 出处联动 | `(pN)` 可切换 PDF 页；块出处会打开原文并高亮块；图表出处会跳到节页中的裁切图。现有块模型记录首页页码及纵向位置，但普通文本块没有完整 PDF 矩形，PDF 视图也没有高亮层。 | 建立统一的出处定位服务，区分“定位到页”和“准确高亮文本”；不能用页级位置冒充精确命中。 |
| PDF 操作 | PDF.js 当前每次只把一页渲染到 canvas。缩放入口是按钮，重绘后滚动位置重置到左上角；没有文字层、滚轮缩放或触控板局部缩放。 | PDF 阅读器需要页加载、缩放锚点、文字层与高亮层的整体升级。 |
| 选区 | 从应用的原文 DOM 选区提问已存在，并扩展为块区间；PDF canvas 上不能选字。翻译只对当前节或全文调用，结果按 `sectionId:language` 保存。 | 用户提出的 PDF 选区翻译与提问需要文字层及从 PDF 文本到论文块地址的可靠映射。 |

## 建议的 v2.0.0 主线

**统一阅读工作台。** 读者从地图选择章节后，在同一阅读上下文中查看 L2 要点、原文、译文、深挖产物和 PDF 证据，并能从任一出处返回相同位置。地图保留全文概览的作用，但不再承担一套与原文隔离的节页导航。提问作为当前阅读位置的操作入口，保留全文提问能力。

推荐先以提取的原文为主要阅读表面，PDF 作为可展开的证据表面。这样能复用现有块地址、原文选区和翻译数据。PDF 也应允许独立阅读、缩放和选区操作；是否把 PDF 改成默认主视图，应在交互原型与真实论文走查后决定。避免固定同时展开节树、原文、译文、PDF 和问答五列。

## 工作顺序

1. **建立行为基线并审查代码边界。** 选取导入、建图、切节、点出处、翻译、提问、PDF 浏览的代表性路径；记录现状与回归检查。重点检查 `main.js` 中阅读状态的所有权、PDF 绘制生命周期、问答消息存储和 Rust/JS 地址契约。使用 `ce-simplify-code` 分批处理已稳定、可证明行为不变的代码；界面与协议行为调整另行设计。目标是减少修改同一阅读动作时需要协调的状态和文件，不以删掉多少行为或多少行代码计分。
2. **升级 PDF 阅读底座。** 让页面按需渲染，并支持页码导航、适配宽度、以指针位置为锚的 Ctrl+滚轮缩放，以及在目标 WebView2 设备上验证触控板双指缩放。缩放后保留正在查看的局部位置。加入可选择的文字层，验证不同来源 PDF 的文本顺序与选区行为；扫描版和无文字层 PDF 要明确降级。
3. **统一出处与阅读位置。** 对 L1、L2、L3、原文块、图表和问答引用建立同一定位接口，统一驱动章节选择、原文滚动与 PDF 页跳转。页级定位可先交付；文本精确高亮必须有可靠坐标或匹配结果，失败时仅显示页级定位。普通文本块目前仅有首页纵向位置，精确高亮可能需要扩充块几何数据及旧书库兼容处理。
4. **重排章节阅读表面。** 地图作为全文概览，章节内按“要点、原文/译文、深挖、出处”组织连续阅读。译文先兼容现有整节记录；如要做到段落并排，需要引入稳定的块级译文锚点，并处理原文修订与旧译文的失效或回退。提问入口保留当前章节与选区绑定，避免频繁切换顶层 tab。
5. **把 PDF 选区接入现有操作。** 在文字层选中片段后，提供“翻译”和“提问”。提问优先复用现有片段绑定和块区间出处；当 PDF 文本与块模型无法可靠对应时，保留选中文字、PDF 页码及选区位置，明确标识为页级引用，不伪造块出处。选区翻译可先作为即时结果，不自动覆盖已保存的整节译文。
6. **升级问答为受限的论文取证 harness。** 保留已有多轮历史与绑定提问，给问答增加只读的按需取证、可见的工具轨迹、轮次与上下文预算、取消和失败恢复。优先复用现有深挖流程的只读取证能力；限制在当前论文，避免扩展成通用 agent 工作台。先验证“回答能否找到并准确引用证据”，再决定是否引入更复杂的规划与记忆机制。

前五项构成阅读体验的主链，其中 PDF 文字层、地址映射和阅读位置会互相制约。第六项可以在主链的地址契约稳定后推进。应用内更新是 v2.0.0 的交付基础设施；发布后尚未完成的升级、干净安装、卸载走查及书库恢复可靠性，应与更新器一起验证。

## 解析侧车体积与后端选择

这项需求与阅读链路直接相关：v2.0.0 想实现的 PDF 选区、产物出处高亮，都依赖解析结果里的稳定文本、章节、页码及坐标。评价替代方案不能只看 OCR 识字率。

### 已确认的体积与现有能力

本机留存的 v1.1.0 NSIS 安装包为 **716.9 MiB**。工作区当前侧车目录实测 **1591.6 MiB**，其中模型约 **536 MiB**，Python 与钉版依赖约 **1053 MiB**，`torch` 目录约 **438 MiB**。侧车清单仍记录 2026-09-10 构建时的 **1,576,869,467 字节，约 1504 MiB**，与当前目录不一致；两者不能混作同一次测量。当前工作区目录也不能直接等同于留存安装包的内容，压缩后的减量必须重新打包实测。

构建脚本已有 `bundled` 与 `download` 两种变体，Rust 侧已有 `pdfparse.bootstrap@1`、模型目录查找和状态检查。但现有 `download` 变体只随包放嵌入式 Python 与下载器，首次补齐时还要在线安装全部 Python 依赖；应用界面也没有启动 bootstrap 的入口。它不等于“应用内只下载模型”。历史打包记录测得：完整随包约 728 MB，旧下载变体约 36 MB，但后者首次需下载约 322 MB 依赖和 537 MB 模型。当前版本的具体压缩体积仍需重新构建实测。

**建议先试验第三种打包形态：随安装包提供已验证的侧车运行依赖，模型由应用按需下载。** 首次需要解析时明确显示下载量、存储位置和离线限制，允许提前下载、取消、重试；完整下载并校验后再激活模型。现有状态检查主要依赖必需文件是否存在，正式下载还需固定模型版本与内容校验。模型与 Docling 版本绑定，保留旧版本直到新版本验证成功。解析原有论文不应因模型未下载而影响浏览已有产物。模型缓存宜放在应用管理的数据目录，避免书库迁移或删除意外带走运行资源。此方案可避免每次安装都携带约 536 MiB 模型，但不会减少用户下载完成后的总占用；剩余依赖仍很重，是否继续减少 `torch` 等运行依赖，应单独测量与回归，不能靠删包猜测。

### 替代解析路径的阶段性判断

| 路径 | 当前证据 | 判断 |
| --- | --- | --- |
| 本地 Docling | 项目历史的 10 篇论文对照验证了复杂章节、双栏顺序、图表和页坐标；现有 Rust 映射直接消费 DoclingDocument JSON。官方支持[预下载模型并指定本地 artifacts 目录](https://docling-project.github.io/docling/usage/advanced_options/)。 | 保持质量基线；**Trial**：模型仅在应用内下载，实测安装包大小、首次解析和故障恢复。 |
| 专用云端文档 OCR | [Mistral OCR 4 系列的结构块](https://docs.mistral.ai/studio/document-processing/basic_ocr)可返回段落级框和块类型；[Azure Document Intelligence Layout](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0)提供段落角色、坐标、表格等。项目尚未在论文集上验证两者的坐标帧、图表归属和编号保真。历史百度 PP-StructureV3 对照出现坐标帧偏移，说明接口有 bbox 并不等于能直接高亮原 PDF。 | **Trial**：先挑一个服务、固定模型版本做 BYOK 适配和同集对照，验证通过后再作为用户可选解析后端。云端解析须明示 PDF 上传、费用和失败后的本地回退。 |
| 通用多模态大模型 | [Gemini 的 PDF 理解接口](https://ai.google.dev/gemini-api/docs/document-processing)能读取整份 PDF；官方说明并未提供本项目所需的稳定块地址和页内坐标契约。历史 PaddleOCR-VL-1.6 实测还出现整篇提交静默缺页，需要分段规避。 | **Hold**：可探索难页解释或局部补救；在证据坐标、数字/公式保真和页完整性达标前，不作为默认块模型来源。 |
| 无模型原生提取 | [Docling NativePdfPipeline](https://docling-project.github.io/docling/reference/pipeline_options/)无需布局、OCR、表格模型，但输出缺少可靠阅读顺序、标题和表格。项目历史的轻量 `parser.js` 在罗马编号、无编号、双栏和附录论文上出现结构错误。 | 可用于即时预览或诊断；当前证据不足以替代精读解析。 |

上表的 `Trial` 是试验建议，不表示新服务已达到产品质量。历史对照与打包记录保存在 Git 历史 `35324e7` 的 `docs/background/2026-09-09-harness-validation/docling-sidecar-validation.md` 和 `docs/background/2026-09-10-docling-sidecar/packaging-measurements.md`；它们不能代替对 2026 年现行云端服务的重新实测。

### 同集对照与产品边界

沿用现有 10 篇论文及回归夹具，并补充有真实文字的扫描页样本。所有后端先转换到同一块模型候选形状，再比较章节和双栏顺序、原文及公式/表格数字、图表与脚注、页完整性、PDF 坐标叠加，以及最终建图和出处跳转。记录安装包与模型下载量、首次可用时间、每篇延迟、实际费用、失败重试和隐私成本。缺页、伪造出处或坐标无法对齐应单列失败，不能被平均文本相似度掩盖。本轮未向云端服务提交论文，也没有完成新的服务实测；上述云端判断仅来自官方接口文档和项目历史对照。

用户选项建议先保持简单：默认本地 Docling，模型由应用管理；经同集验证的云端 OCR 才显示为可选解析方式。每篇论文记录所用后端及版本，重新解析时先保留旧块模型，待新结果通过校验再切换。普通多模态问答可以继续使用用户配置的模型端点，但不能仅因端点支持图片或 PDF，就把它显示为等价的结构化解析后端。

## v2.0.0 起的应用内更新

当前客户端采用 Tauri 2 的 Windows NSIS 安装包，但 `Cargo.toml` 未引入 updater 插件，`tauri.conf.json` 也未配置更新端点与更新产物；仓库只有测试 CI，没有发布工作流。v1.1.0 安装版因此不能在应用内自行升级。**v2.0.0 应作为首个内置更新器的版本发布；v1.1.0 用户需手动安装 v2.0.0，此后的版本才可走应用内更新。**

建议使用 [Tauri 2 官方 updater](https://v2.tauri.app/plugin/updater/) 和现有 GitHub Releases。为 Windows 安装包生成 updater 签名及 `latest.json`，发布时把版本、安装包、签名和清单作为同一次发版核对；静态清单可以从 GitHub Releases 的 `latest/download/latest.json` 提供。签名公钥随客户端发布，私钥只保存在受控发版环境并做好备份；Tauri 的 updater 签名与 Windows 安装包的代码签名是两件事。更新器配置只允许 HTTPS 端点，不依赖未来云服务器。当前仓库没有自动发版流程，先把构建、签名、清单生成和发布核对做成可重复的流程，再考虑无人值守发布。

界面在设置或“关于”处显示当前版本，并允许检查更新；有新版本时显示版本号、更新说明、安装包大小及下载进度，下载失败可重试。下载后由用户确认安装；正在解析或生成时先结束或取消任务，再触发安装。Tauri 文档说明 Windows 安装阶段会自动退出当前应用，因此要在退出前完成数据落盘。大侧车与模型应分离管理：应用更新下载的是安装包，Docling 模型下载有独立的版本、校验与状态，不能把模型更新冒充应用版本更新。Tauri 的更新包仍是完整安装包；体积收益以模型拆出后重新打包实测为准，不预设增量补丁。

发版验收至少覆盖 v1.1.0 手动升级到 v2.0.0、v2.0.0 经签名测试更新到更高测试版本、取消/断网/签名不匹配、活动任务退出、安装后书库仍可读，以及旧书库迁移失败时的恢复。数据库启用 WAL，迁移前的备份或快照必须由 SQLite 一致性机制完成，不能只复制 `library.sqlite` 主文件；应用包安装失败和数据库迁移失败是两个独立故障。更新后写入更高版本数据库时，旧应用可能拒绝打开该书库，降级不能仅靠重装旧安装包承诺。

## 已有数据库与跨端准备

客户端**已经有 SQLite 数据库**：Rust 在应用数据目录下打开 `database/library.sqlite`，启用外键和 WAL，使用 `PRAGMA user_version` 从 v1 迁移到当前 v6。论文、章节、阅读产物、译文、问答、阅读位置、活动记录和设置等存在数据库中；PDF 与其他附件存在书库的 `attachments` 分区。前端通过版本化 Rust 桥接命令和 DTO 使用这些数据，不直接访问 SQLite。缺口是跨设备阅读副本和同步协议，不是数据库引擎。

建议把 v2.0.0 的准备工作限定为当前阅读改造需要的稳定契约：为论文内容、解析块、出处位置和产物定义可演进的标识与内容版本；明确哪些字段进入移动阅读副本，哪些字段（API Key、完整设置、未选论文及运行时模型）始终留在 Windows；重解析或重建产物后，使旧出处、译文和位置能识别失效或回退。对外以版本化 DTO/HTTP 契约传输内容，不传整份 SQLite 文件或表结构。旧书库升级要有迁移测试和一致性备份，避免将来因阅读地址改动而丢失积累。

既有 [云端同步服务 #25](https://github.com/attackingjensen/paper-30min/issues/25) 已确定未来使用独立 FastAPI 服务和服务器侧 SQLite，保存主动选取论文的不可变移动阅读版本、附件、阅读位置、删除标记及可恢复的同步操作；[Android 阅读伴侣 #26](https://github.com/attackingjensen/paper-30min/issues/26) 消费该副本并缓存离线阅读内容。Windows 本地书库仍是论文内容权威来源。这两项尚未启动，v2.0.0 不需要为此迁移到服务器数据库或提前建设账户系统。真正要先稳定的是内容单位、版本、出处和阅读位置的语义；云端和 Android 可按既有规格另行实施。

## 验收重点

- 点地图要点、节摘要或深挖出处后，读者能看到对应原文及 PDF 页；只有坐标可信时才出现精确高亮。
- 切章节、打开 PDF、返回提问后，当前章节、PDF 页和阅读滚动位置保持一致。
- Ctrl+滚轮和触控板缩放在安装版 WebView2 中可用，缩放围绕指针附近内容，页面不会跳回左上角。
- 可选中文字的 PDF 能直接选择片段并翻译或提问；无法提取文字的 PDF 有清楚的降级路径。
- 已有译文和问答记录仍可读取；新问答保留多轮语境，并能回看使用过的论文证据。
- 模型未下载时已有论文和产物仍可阅读；下载失败或中断不会留下被标为就绪的半套模型。
- 解析后端选项只展示经过同集对照、可满足块地址与 PDF 定位要求的实现；每次结果能回溯到后端版本。
- v2.0.0 安装版可以检查更新，显示版本和说明，并验证下载及安装包签名；从 v2.0.0 到后续版本的测试更新不损坏书库和附件。
