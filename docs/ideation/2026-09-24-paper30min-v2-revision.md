## PDF 证据阅读的约束

来源矩形经身份核验后用于精确高亮，旧数据不足时回退页级定位；不能把页级线索画成精确命中。选区不能可靠对应书库原文块时仍可翻译与提问，实际文字或截图与附近块上下文分开。连续阅读、跨页选区、双栏、扫描页、旧数据以及 WebView2 缩放和模式切换已有本版验收证据，限制见发布说明。v1.3.0 不重排地图、原文、译文、深挖和问答的整体信息架构。

## 后续阅读与问答取舍

统一工作台应让地图作为全文概览，同时保留 PDF 独立阅读与原文阅读，不把节树、原文、译文、PDF 和问答永久挤成多个窄栏。默认以 PDF 还是提取原文为主，需等 v1.3.0 真实论文走查后决定。块级译文若加入，必须处理块地址变化和旧整节译文；问答已支持多轮历史，未来价值在证据准确性和可回看取证过程，而不是重做聊天记录。

## 解析与跨端试验门槛

解析后端统一按同一论文集比较章节与双栏顺序、公式和表格数字、图表归属、页完整性、PDF 坐标叠加、建图和出处跳转。专用云端 OCR 要明示上传、费用和失败回退；通用多模态模型或无模型原生提取尚未证明能稳定生成本项目的块地址。模型单独下载须绑定解析器版本、校验完整性，不能把半套下载标为就绪。历史对照和旧打包测量可在 Git 历史 `35324e7` 的 `docs/background/` 中追溯，试验前需要重新测量现行版本。

Windows 本地书库已采用 SQLite 和版本化 Rust 桥接。未来移动副本应通过版本化内容契约传输，不直接同步 SQLite 文件，也不包含 API Key、本机设置或未选论文。旧书库迁移和备份须使用 SQLite 一致性机制；WAL 模式下仅复制数据库主文件不足以证明可恢复。

## v2.0.0 技术栈边界（2026-10-09 确认）

- 外壳维持 Tauri 2，不迁移 Electron。当前痛点（流式渲染、PDF 阅读、界面美观）均为外壳无关问题；换壳会使 smoke、原生集成、更新器与安装版矩阵的既有验证证据清零。触发再议条件：必须使用的 npm-only 关键库无法经侧车接入；WebView2 在实际环境出现可测量故障且影响面扩大；必需的新 Web 平台能力不能容忍 WebView2 跟进延迟；演变为多用户分发且需要插件体系。
- 前端迁移到 React + TypeScript（构建与样式方案在 v2.0.0 spec 中确定）。驱动因素：阅读工作台同时维护论文位置、PDF 状态、流式回答、阶段产物与布局五类状态，命令式 DOM 维护成本已不可持续（主控单文件超 4500 行且仍在增长）。
- 流式渲染单列重做：首选评估 Streamdown（面向不完整 Markdown 的流式渲染）；出处语法与 Markdown 排版职责分开。
- PDF 不换引擎（保留 PDF.js），分两层重做：阅读工作台交互架构、页面调度（虚拟化、可视区渲染、过期渲染任务取消）。
- 保留：Rust 业务层、SQLite、版本化桥接命令、阅读协议与提示词、解析侧车、应用内更新。
- 云端服务与 Android 伴侣不改变上述边界：服务端独立选型（Node/TS 合理），移动伴侣走版本化内容契约，可复用 React 组件层；Electron 对移动端无贡献。
- v2.0.0 的正式 spec 另行产生，输入包括本文件、全量简洁性审查的保留/重写清单（Linear 项目 P-STE-3）与用户摩擦清单。参考讨论：[ChatGPT 技术栈讨论](https://chatgpt.com/share/6ac8cce2-2e30-83ee-8307-2db14d659c61)（2026-10-09 读取，结论已经本文档过滤，以其原文为准时需重读）。
