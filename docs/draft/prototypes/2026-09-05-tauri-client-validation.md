# Tauri 双端可行性验证

本文是 [客户端形态设计](../2026-09-05-client-platform-design.md) 的原型范围与验收建议，尚未实施，不代表正式技术选型。原型代码位置、分支、安装包与实测结论将在实施时补充。

## 要回答的问题

Tauri 是否能在 Windows 与 Android 上可靠承载现有 Web 阅读能力，并让两端共享有实际价值的 Rust 本地能力，值得作为正式客户端基础？

## 范围与隔离

- 使用独立原型分支与工作目录，不直接改造当前正式应用入口。原型代码不合入主分支，验证结果与对应提交另行留档。
- 使用独立应用标识、数据目录、测试 SQLite 数据库和附件目录，显示原型身份；仅使用示例论文、公开测试材料与模拟阅读成果。
- 复用现有 Markdown、MathJax 和 PDF.js 资源，建立最小书架与阅读入口。Windows 和 Android 可采用不同导航布局，共享适用的阅读模块。
- Rust 只实现最小的记录读写、附件访问及阅读位置保存，用同一份可共享逻辑在两端运行；平台目录与文件选择允许分别适配。
- 流式与内容版本接口使用本机测试服务。Android 调试可通过 USB 端口转发连接，不依赖公网、域名或 GitHub Actions，也不恢复产品的局域网入口。
- 暂不实现正式账号、完整同步服务、真实书库迁移、完整数据库迁移体系、自动升级、界面改版或正式签名流程。原型使用独立测试签名；应用升级保留数据仍需验证。

## 验证矩阵

| 验证项 | 场景 | 通过证据 |
| --- | --- | --- |
| 安装与生命周期 | Windows 安装后从入口启动、退出；Android 安装 APK 后启动、返回、再次打开 | Windows 运行不依赖开发服务器或 Python，不出现终端；退出后无原型遗留进程；Android 返回路径与重开正常 |
| 阅读渲染 | 两端打开包含中文、表格、行内与块级公式的阅读内容；打开普通论文 PDF 与较大 PDF | 本地资源加载完整，无空白或公式损坏；PDF 翻页与缩放可操作；记录文件大小、页数、首屏耗时与异常 |
| 共享本地能力 | 两端使用同一 Rust 记录读写逻辑，保存测试论文、附件与阅读位置，关闭后重开 | 数据与附件可读，阅读位置恢复；记录共享代码与平台专有代码各自职责，不能以两套独立实现冒充复用 |
| Windows 流式响应 | Rust 网络路径接收模拟 SSE，覆盖中文分片、结束标记、中断及中断后重试 | 内容持续出现、结尾完整；取消后旧任务不再写入当前视图；窗口关闭后请求停止 |
| Android 离线与恢复 | 缓存完成后断网；切后台再返回；结束应用进程后重新打开 | 论文文字、公式和已缓存 PDF 可读；最后保存的位置恢复；未缓存附件有明确状态，无空白或无限等待 |
| 版本切换 | 测试服务提供两个内容版本；下载中断；正在阅读时收到新版 | 中断后仍可读旧的完整版本；新版就绪后退出阅读页再切换；位置匹配失败时保留旧位置并允许选择章节 |
| 覆盖安装 | 两端分别安装第二个原型版本，沿用应用标识与测试签名 | 原型书库、附件及位置保留；记录实际安装包和系统版本，不据此宣称正式迁移体系已验证 |

2026-09-05 调整 WebView2 依赖验证口径：两台目标机器（开发机与仓库持有者主力机）均为预装 WebView2 的 Windows 11，"缺 WebView2 时安装器补装"路径在真实使用中不会被触发，此项标为未验证并注明该理由；若未来纳入 Windows 10 等无预装 WebView2 的目标机再补验。安装生命周期、覆盖安装与数据保留改在开发机新建的干净本地账户下验证（用户级环境变量不跟随，接近新机体验）；仓库持有者机器仅在原型就绪后做一次真实环境安装确认（装、启动、读一篇）。

Android 模拟器可用于构建和基础走查，PDF 性能、触摸操作及后台恢复以目标真机为验收依据。切后台恢复不代表支持后台持续同步。

目标真机覆盖协作开发者的荣耀手机与仓库持有者的小米手机，两者均运行各自设备可用的最新系统；具体机型、Android 基础版本和 WebView 版本在验证时记录。两种设备分别记录结果，不将一台通过视为另一台已验证。

## 测试材料与记录

- 优先使用仓库示例 PDF、公开且可重复取得的长论文或图表较多的 PDF，以及固定的模拟 Markdown 阅读成果；不使用真实私有书库或 API Key。
- 记录 Windows 版本、WebView2 版本、手机型号、Android 版本及系统 WebView 版本；保留步骤、日志和必要的截图或录屏。
- 首次打开、翻页、缩放与连续操作分别记录表现。初期不承诺未经测量的包体、启动时间或帧率；明显卡顿需定位是 PDF 渲染、文件桥接还是外壳问题。
- 每项结论明确区分通过、失败和未验证。未连接真机、缺少构建工具或缺少干净 Windows 环境，不应写成框架失败或已通过。

## 退出与决策

- 关键场景全部通过且平台适配成本可接受：据实推荐 Tauri，正式实现另起任务，不直接继承原型中的临时实现。
- 某项失败：先判断属于 Web 阅读器、共享核心、平台插件还是外壳本身；仅在原因需要时用备选方案复验，不预先同时建设多套完整原型。
- Windows 可行而 Android 外壳存在明确障碍：允许评估 Tauri Windows + Capacitor Android，不把统一框架作为必须满足的目标。
- 若问题来自同样运行在 WebView 的 PDF 阅读器，更换 Tauri/Capacitor 不自动构成解决方案，应先验证阅读器改进或原生 PDF 组件。
- 验证结束后保留原型分支与结论索引；正式规格和必要的 ADR 依据验证结论及双方确认另行形成。

## 验证结论（2026-09-05，Issue #20 已关闭）

原型代码存档于 `steven123397/dev` 分支 `prototype/tauri-reader/`（commit e0a9d3b），构建产物（node_modules/target/gen）未入库、可随时重建；验证矩阵逐项实测结果、环境与未验证项记录见 [Issue #20 决议评论](https://github.com/attackingjensen/paper-30min/issues/20)。摘要：Windows 与荣耀真机（BVL-AN16，Android 16）双端关键场景全部通过，据实推荐 Tauri 为正式客户端基础；发现 Android 状态栏安全区适配、网络层归口 Rust、构建镜像配置三项正式实施输入；小米手机、较大 PDF、未缓存附件离线状态、WebView2 缺失补装路径标未验证。
