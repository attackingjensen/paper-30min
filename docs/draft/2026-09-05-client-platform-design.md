# Windows、云端与 Android 客户端形态

本文记录 `grill-with-docs` 讨论中已经确认的方向与尚未解决的分支。它不是已接受规格；完整设计经双方确认并由仓库持有者认可后，难以逆转的决定再进入 ADR。

## 目标背景

- 仓库持有者真正需要的是“电脑导入，未读完时在手机继续阅读”；当前局域网访问只是没有云服务器时形成的替代实现。
- Windows 应用应可下载即用，用户不需要拉取源码、安装 Python 或通过脚本启动。
- Windows 本地书库是论文内容的权威来源。应用不依赖论文阅读云端服务也能运行；需要 arXiv 或模型 API 的功能仍然需要互联网。
- 只有用户主动选择的论文数据才进入云端，不做默认整库上传或自动云备份。
- 现有服务器自有 40 GB 磁盘，剩余接近 20 GB；另挂载基本未使用的 20 GB 数据盘及一个 COS 存储桶。资源分配与存储后端选择留到部署设计时讨论，不作为当前讨论重点。
- 服务器为自有腾讯云轻量应用服务器，位于北京地域，当前没有现成域名。协作开发者有网站部署全流程及 TCR 等服务的使用经验，部署操作不需要从入门开始；是否使用 TCR 由交付方式决定。GitHub CI 账号锁定仍等待仓库持有者处理，不阻塞设计讨论与本地验证。
- 协作开发者使用荣耀手机，仓库持有者使用小米手机，两者均为各自设备可用的最新系统。具体机型、Android 基础版本及 WebView 版本在真机验证时记录，不能从“最新系统”推定两者版本相同。
- 前端采用渐进式重设计：重新梳理桌面与手机的导航、布局和操作体验，但保留现有核心使用逻辑、阅读能力和已确认需求，不进行脱离需求的全面颠覆。

## 已确认方向

- 当前最多由协作开发者与仓库持有者 2 人使用，没有面向更多用户的需求。管理员直接创建 `diaozx` 和 `liangjq` 两个独立账号，客户端记住登录，忘记密码由管理员手动重置；保留账号隔离，不开放公众自助注册，不建设邀请系统、邮件服务或专门的管理界面。此处仅记录设计，尚未创建实际账号。
- Android 第一阶段是阅读伴侣：先覆盖阅读与阅读位置，后续再考虑问答、导入、生成和整理。
- 用户通过移动书架选择需要在 Android 继续阅读的论文。
- 界面使用“云端同步”，不使用“发布”。论文内容同步由用户手动触发，系统仅上传发生变化的数据，全部成功后原子切换云端版本；上传未完成时，Android 继续使用旧的完整版本。
- 移动书架显示“未同步、有更新、同步中、已同步、同步失败”，提供逐篇与批量云端同步操作。这些状态描述论文内容同步，不表示阅读位置同步状态。
- 移动阅读副本包含论文信息、章节原文和阅读成果；PDF 由用户逐篇决定是否包含。
- 移动阅读副本中的阅读成果包括精读结果、翻译、回想卡片和论文问答；不包含 API Key、模型设置或仅存在于 Windows 的应用设置。
- 一个账号第一阶段允许登录多台 Android 设备；每台设备维护自己的缓存，阅读位置由云端统一同步。
- 云服务器是受信任的数据处理方，通过 HTTPS、账号隔离和访问控制保护用户主动同步的数据；第一阶段不做端到端加密。
- Android 缓存论文信息、章节原文和阅读成果；用户选择下载的 PDF 可以离线阅读。
- Windows 与 Android 都可以更新阅读位置，冲突时采用最后写入优先，并保留客户端时间、设备 ID 和版本信息。
- 对已同步到云端的移动书架论文，两端联网且已登录时自动同步阅读位置，与手动进行的论文内容同步分开处理。
- 两端内容版本不一致时各自保留阅读位置，不强行跳转；新版论文内容同步完成后尝试对应章节，对应失败时由用户选择章节。
- Android 联网打开应用时自动检查并更新已同步到云端的论文文字与阅读成果，PDF 按用户的下载选择处理。正在阅读时提示有新版，退出当前阅读页后再切换，避免中途改变内容。
- PDF 支持云端按需读取与本地下载两种模式：在线查看不必先完整下载，服务端需支持按页读取所需的范围请求；用户主动下载或已选择离线阅读的 PDF 保存在 Android 本地。离线阅读只对已缓存内容负责。
- Android 首版 PDF 阅读只要求翻页、页码跳转、双指缩放和阅读位置恢复，不做搜索、文字选择或批注。
- Android 切到后台时不保证继续下载；系统暂停后，回到应用前台再继续。已完成缓存的内容始终可读。
- 离线产生的旧阅读位置重新联网后不自动覆盖已有的较新位置；旧位置保留为可选项。在线状态下的阅读位置更新仍采用最后写入优先。
- 删除 Windows 本地论文前明确提示；确认后将云端删除加入队列。服务器暂时不可用时保留待删除状态，成功后删除移动阅读副本。
- 论文内容同步使用开始时的本地内容版本；同步期间的新修改标记为“有更新”，不覆盖正在上传的临时版本，下一次云端同步再处理。
- Windows 直接请求用户配置的模型提供方，API Key 仅保存在 Windows 本地；云端不承担模型代理，也不保存 API Key，Android 第一阶段不调用模型。
- 登录采用用户名和密码，客户端保存可撤销的设备会话；不建设邮箱找回或公开注册。管理员手动重置密码后，所有旧设备会话失效。
- 云端采用全服务器共享容量上限，初始设为 5 GB，不设每账号配额，后续按实际使用情况调整。应用容量上限与服务器物理存储容量分开考虑，具体存储部署暂缓讨论。
- 移出移动书架会删除云端副本但保留 Windows 本地论文；删除本地权威论文时，明确提示并传播云端删除。
- 正式 Windows 应用倾向使用 SQLite 保存结构化记录，以本地文件保存 PDF 和图片。
- Windows 第一版提供普通安装包，安装后从桌面或开始菜单打开，应用数据独立保存，暂不同时维护便携版。
- Windows 与 Android 第一版均通过手动下载安装新版本升级，覆盖安装保留书库和设置，暂不开发自动更新。
- 现有浏览器书库通过整库导出文件迁入 Windows 应用，首次使用时提供导入入口，确认导入成功前保留原书库；API Key 不进入迁移文件，在新应用中重新配置。
- Android 第一版直接分发签名 APK，不上应用商店；后续版本沿用同一签名以支持覆盖升级，签名密钥需妥善保管和备份。
- 每个账号第一阶段维护一台主要 Windows 设备，Android 作为阅读伴侣；更换 Windows 设备通过迁移，不做多台 Windows 共同编辑同一书库。
- Windows 关闭窗口时，有生成或同步任务应明确提示等待或停止；默认不因关闭窗口转入托盘后台运行。可恢复的数据按任务本身的持久化规则保留。
- 正式实现前优先制作不承载真实数据的 Tauri Windows + Android 小原型，保留 Web 阅读器，验证本地 PDF、公式、Windows 流式输出、Android 离线缓存及后台恢复。验证通过后再决定是否以 Rust 实现客户端本地能力，不先迁移全部业务；这替代此前优先验证 pywebview 的顺序，原型尚未实施。
- 当前局域网访问不再作为目标能力保留。它无法替代公网移动阅读，并增加后续迁移与测试负担；移除时间和实施方式尚未形成 Issue。
- 云端采用独立 Python FastAPI + Uvicorn 同步服务，结构化数据先使用 SQLite，按当前 2 人规模采用单实例部署。现有 `server.py` 的模型转发和本地资源接口不作为公网同步 API。
- 云端采用 Docker Compose 部署并接入 HTTPS 反向代理；具体代理配置与是否经 TCR 分发镜像留到部署时决定。GitHub Actions 解锁前可本地验证和构建。
- 暂缓域名购买、公网入口与备案安排，先完成客户端原型验证；这些事项不是原型的前置条件。正式部署前确认北京服务器对两人自用 App API 的接入要求；直接使用 IP 不视为免除备案要求的依据。

## 技术选型建议（待确认）

- Windows：比较 pywebview + WebView2 + PyInstaller 与 Tauri + Rust；尚未选定正式外壳。前者能沿用 Python 本地能力，后者可用 Rust 承接本地存储、文件与网络能力，并与 Android 共享适用的客户端逻辑。现有 Python 主要是资源服务与转发，正式 SQLite 书库和云端同步尚未实现，不应仅以保留现有 Python 为由排除 Tauri。
- Android：比较 Capacitor、Tauri Android 与 Kotlin 原生界面加 WebView 阅读器。前两者均可复用 Web 阅读渲染，Tauri 可进一步共享 Rust 核心但增加 Rust/NDK 构建与平台插件适配；Kotlin 方案需要单独实现原生界面及其与阅读器的通信。现有 `app.js` 不能整体复用为手机入口，所有方案均需验证真机 PDF 性能、文件访问及离线恢复。
- Rust 的候选范围是客户端本地能力及可共享的同步核心，不默认重写 Web 阅读界面、现有全部 JavaScript 或已选定的 Python 云端。Tauri 同样依赖 WebView，不能据此承诺 PDF/公式渲染更快或安装包必然达到某个体积。
- 部署阶段再选择公网入口：按接入要求使用现有北京服务器、另用香港或海外服务器承载同步 API，或采用私有组网。三者均未选定，不据此购买服务或配置组网；若采用域名，仅提供 API 即可，不要求开发网页端。
