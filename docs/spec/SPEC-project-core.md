# Spec: project-core

> 状态：已批准  
> 所属能力地图：[文本中心阅读核](capability-map.md)  
> 依赖：无  
> 下游：`document-core` 及全部工程内能力

## Objective

为文本中心的 Paper30Min 提供一个**本地、开放、可搬迁、可恢复**的工程容器。工程身份不再依赖 PDF，正文导入与工程创建分离；来源快照、当前正文 revision 和普通用户文件各有明确的所有权与提交边界。

目标用户是以 arXiv 为主要论文来源，同时仍需导入本地 PDF、保存笔记与精解、使用持续 Agent 会话的个人读者。

本模块成功时，应满足：

- 没有 PDF 也能创建、搬迁和重开有效工程。
- 首次导入失败不会丢掉工程身份与可恢复现场，也不会被误报为正文已可读。
- 来源快照不可变，当前正文只有一个明确指针，修正或更新不会静默覆盖用户修改。
- 普通参考文件不再需要登记为“材料”，旧 v1 书库批量导出入口不再存在。

## Scope

### In scope

- 工程清单、工程身份、主论文身份和保留目录。
- 创建工程、首次导入的持久化与恢复边界。
- 来源快照、当前 revision、候选内容和提交指针的所有权。
- 普通文件树、普通 Markdown 与受管内容的区分。
- 相对路径、完整性校验、原子提交、外部修改检测和整体搬迁。
- 默认工程目录、最近工程等本机偏好与工程数据的边界。
- 对旧 `formatVersion: 1` 的明确识别与拒绝；实际兼容策略由 `legacy-projects` 决定。

### Out of scope

- arXiv 网络获取、HTML 转换和资产规则，属于 `arxiv-import`。
- PDF 云端解析与来源特有诊断，属于 `pdf-import`。
- 文档树、句子、锚点和三方合并的数据结构，属于 `document-core`。
- 阅读、翻译、批注、成果卡片、双栏、Agent 工具和 PDF 同步。
- 旧 v2 工程的迁移或只读兼容，属于 `legacy-projects`。
- 旧 v1 书库扫描、SQLite 读取和 PDF 批量导入；该产品能力取消。
- 安装包、应用更新器、云同步和移动端。

## Tech Stack

- Windows 桌面端：Electron 主进程、Node.js utility process、受限 IPC/preload。
- TypeScript 与 React，沿用当前 `app/` 工程和依赖锁定方式。
- Node.js 24；本地文件系统与 JSON／普通文件为持久化权威。
- Pi 原生 JSONL 会话继续保存在工程内，但本模块不定义 Agent 行为。
- 不使用 SQLite，不自动初始化 Git，不引入远程工程后端。


针对本模块的真实 Electron 回归应按用例标题运行：

## Project Structure

### 仓库代码边界

```text
app/src/main/              Node 工程命令、持久化和提交实现
app/src/shared/contracts.ts 工程与 IPC 共享类型
app/src/renderer/          创建、恢复和文件树入口；不包含持久化权威
app/tests/                 真实 Electron 高层回归与受控服务 fixtures
docs/spec/                 已批准能力地图和模块规格
```

现有 `project-service.ts`、`contracts.ts` 和 `desktop.spec.ts` 是改造输入，不要求保留其中的 PDF 必需、`materials`、`map` 或旧导入假设。

### 新工程磁盘契约

```text
工程文件夹/
  paper30min.json             # 轻量清单与 current 指针
  paper/
    revisions/<revisionId>/   # 已发布的受管正文 revision
  sources/
    <sourceSnapshotId>/       # 不可变来源快照及来源元数据
  notes/                      # 普通 Markdown，按需创建
  explanations/               # 普通 Markdown，按需创建
  memories/                   # 普通 Markdown，按需创建
  tmp/                        # 普通临时文件与用户候选成果
  .paper30min/
    revisions/                # revision 元数据
    imports/                  # 首次导入及恢复记录
    staging/                  # 尚未发布的受管候选
    cache/                    # 可重建缓存，不是内容权威
  .pi/
    sessions/                 # Pi 原生会话
```

不预建空成果目录。`paper/`、`sources/`、`.paper30min/` 和 `.pi/` 是受管区域；文件树可以将正文和来源呈现为专门的只读入口，但不得把 staging、未引用 revision 或缓存伪装成普通成果。

## Code Style

共享契约使用 TypeScript interface、明确的可空状态和两空格缩进；Node ESM 的相对导入沿用现有 `.js` 后缀。清单只保存身份和指针，不重新登记普通成果：

```ts
export interface ProjectManifest {
  formatVersion: 2;
  id: string;
  name: string;
  paper: {
    id: string;
    currentRevision: string | null;
  };
}
```

- `id` 与 `paper.id` 是应用生成、持久化且不随路径变化的 UUID。
- `currentRevision` 是 revision ID，不是文件路径或内容哈希。
- `null` 仅表示工程已创建但首次正文尚未提交。
- 清单不包含 `materials`、`map`、`explanations`、`translations` 或 PDF 必需字段。
- revision 元数据记录正文相对路径、来源快照 ID、本地基线、内容摘要和提交信息；具体文档内容结构由 `document-core` 定义。

## Behavior Contract

### 1. 身份与权威

1. 一个工程只有一篇主论文；`paper.id` 在首次导入、原文修正、arXiv 更新和 PDF 重解析时保持不变。
2. 工程路径、显示名称、来源 URL、PDF 哈希和 revision ID 都不能替代工程或论文身份。
3. 来源快照用于追溯、对比和重新处理；**current 指向的结构化正文才是界面与 Agent 的唯一当前阅读权威**。
4. 普通参考文件可以放在非保留目录，包括 PDF、图片和其他材料。它们是普通文件：
   - 不分配登记身份，不写入清单，不提供材料特有的重新关联或哈希保护。
   - 不能通过移动或改名将其冒充主论文；只有明确的来源导入／更新命令能改变主论文。
   - 移动后的路径链接如何处理由对应链接与成果规格定义，不恢复 `materials` 契约。
5. 笔记、精解、记忆卡片和用户自行创建的 Markdown 不登记进清单。

### 2. 工程创建与首次导入

工程创建和正文可读是两个独立提交点。

**工程创建提交点：**

1. 校验名称、目标父目录和来源输入；父目录必须存在且可写，同名子目录不得覆盖。
2. 通过独占创建取得新工程目录的所有权。
3. 写入 `formatVersion: 2` 清单、`paper.id`、`currentRevision: null` 和可恢复导入记录。
4. 清单与恢复记录完整持久化后，工程创建成功，可以登记到最近工程并开始导入。
5. 最近工程登记失败不得删除有效工程；应明确提示，并允许通过路径手动打开。

**正文可读提交点：**

1. 来源模块把快照和候选写入受管区域，当前指针尚未改变。
2. 候选必须达到对应来源模块定义的“可阅读”条件；允许带明确警告，不要求 LLM 审阅或零警告。
3. 受管内容完整落盘并验证后，先发布 revision 元数据，再以原子操作推进 `currentRevision`。
4. 只有 current 非空且对应 revision 通过完整性检查，界面才能显示“正文可读”。
5. 初次导入失败、停止或应用退出后，保留工程、导入记录和已完成的受管内容，提供重试或恢复；不得自动删除工程，也不得显示空白原文冒充成功。

`currentRevision: null` 只有在存在有效首次导入记录时才是合法状态。缺少 current 且没有恢复记录的工程应报告不完整或损坏，不得自动创建新论文身份覆盖。

### 3. 来源快照与 revision

1. 每个被接受的来源快照都有独立 `sourceSnapshotId`、来源元数据、相对路径和内容摘要。
2. 来源快照一经发布即不可变；重新下载、重解析或更新不得原地覆盖。相同内容可以复用已验证快照。
3. 每次正文导入、修正或更新产生新的 `revisionId`。已发布 revision 的内容不可原地修改，修正通过发布新 revision 完成。
4. 系统只保证保留**全部已接受来源快照和当前 revision**。本地旧 revision 不构成完整历史，不提供任意回滚；在新 current 完整提交后可以清理其内容，但不得删除来源快照。
5. 崩溃或取消留下的 staging、未引用 revision 和候选不是 current，不得在启动时按时间或文件名猜测发布。
6. 只有能证明属于本应用、未被 current 或活动导入引用的临时内容才可按恢复契约清理；来源快照和用户普通文件不属于临时内容。
7. 不承诺完整本地编辑历史、内置 Git、自动备份或跨设备同步。

### 4. 修正、更新与并发提交

1. 修正和更新请求必须携带其读取时的 `baseRevision`。
2. 发布前再次核对 current；若 current 已不再是 `baseRevision`，拒绝发布并保留候选，要求重新读取或合并。
3. 新来源先形成快照与候选，不因后台检查、网络重试或重新打开工程自动推进 current。
4. 候选内容、revision 元数据和来源快照必须在 current 指针之前完整提交；指针是最后一步。
5. 同一工程进程内的受管写入串行执行；跨进程和外部修改仍须依靠内容摘要与基线复核，不能仅依赖内存队列。
6. current 切换失败时，旧 current 仍须可读取。新 current 已生效后的旧 revision 清理失败只能产生可恢复警告，不能回滚或破坏新 current。

### 5. 普通文件与外部修改

1. 普通文件树直接反映磁盘，不建立普通文件身份数据库。
2. 普通 Markdown 沿用 UTF-8、内容基线、原子保存和外部修改冲突检测；双方修改时保留用户草稿，不直接覆盖。
3. 清单、来源快照和已发布 revision 是受管内容：
   - 外部字节变化必须通过摘要检查识别。
   - 不得把外部修改静默接受为新 revision。
   - 不得用来源快照自动覆盖已发生外部变化的 current；应报告受管内容冲突或损坏并保留现场。
4. 当前 revision 可读不依赖来源快照始终可用；但涉及重新处理、对照或来源核验时，必须明确报告快照缺失或损坏。
5. 文件树忽略隐藏内部目录、`node_modules`、符号链接和受管临时内容，不跟随链接访问工程外文件。

### 6. 路径与安全边界

1. 工程内路径统一使用 `/`，不得包含父级穿越、绝对路径、反斜杠、Windows 保留名称或尾随点／空格。
2. 受管路径解析不得经过符号链接或目录联接；普通文件树中的链接条目不得被当作普通文件递归读取。
3. 清单、revision 元数据和导入记录采用同目录临时文件、同步与替换，失败不得截断旧有效版本。
4. SHA-256 用于完整性和冲突判断，不作为工程或论文身份。
5. 外部原始 PDF 只读复制，不移动、不修改；工程清单不得保存对其运行所必需的外部绝对路径。
6. 工程整体复制或移动后，所有受管引用仍按相对路径解析；机器配置和最近工程记录不随工程搬迁。

### 7. 本机偏好与旧功能边界

1. 默认工程目录、最近工程和应用设置继续保存在 Electron `userData`，不进入工程。
2. 最近工程最多保留 20 项；失效路径不得导致其他工程无法打开。
3. 模型、解析服务和网络搜索凭据不得写入清单、来源元数据、revision 或导入记录。
4. 新工程不创建 `map/`、`materials` 记录、`.paper30min-citations.json` 或 `legacy-imports.json`。
5. 不提供旧 v1 书库扫描和批量导入入口，不读取旧 SQLite；旧 ADR-0009 对应功能退出当前产品范围。
6. 新核遇到 `formatVersion: 1` 时明确报告需要旧格式处理，不得按新清单猜测读取。后续迁移或只读策略由 `legacy-projects` 单独批准。

## Error and Recovery Requirements

以下情况必须保留现场并给出可行动错误，不得静默成功：

- 目标目录已存在、父目录不可写或工程目录不是预期所有者。
- 清单损坏、版本不支持、论文身份重复或 current 指向不存在的 revision。
- 首次导入中断且存在可恢复记录。
- 来源快照缺失、摘要不符或受管正文被外部修改。
- 候选发布时基线已变化、磁盘写入失败或 current 原子更新失败。
- 工程被移动后最近记录仍指向旧位置。
- 普通文件通过符号链接指向工程外，或受管路径包含非法组件。

错误恢复不得通过删除旧工程、重建论文身份、自动采用新来源或清空损坏记录来“修复”。

## Testing Strategy

### 契约与文件系统集成

覆盖清单解析、非法路径、符号链接、原子写入、摘要核验、基线冲突、current 提交顺序和崩溃现场。测试应验证磁盘上的真实文件，而不只检查内存状态。

必须包含以下故障注入：

- 工程目录创建后、清单提交前中断。
- 清单已提交、首次正文未提交时停止或重开。
- 来源快照完成、revision 候选未发布时中断。
- revision 已发布、current 尚未推进时中断。
- current 已推进、旧 revision 清理失败。
- 候选发布前 current 已被另一操作推进。

### 真实 Electron 高层回归

使用生产 preload、IPC、Node 工程进程和临时目录，至少覆盖：

1. 从受控 arXiv 来源创建不含 PDF 的工程，提交后重开可离线读取。
2. 首次导入停止、失败、重试和重开恢复，工程身份始终不变。
3. 本地修正与来源候选的基线冲突，旧 current 不被覆盖。
4. 普通参考 PDF／图片不进入清单，也不能替代主论文。
5. 普通 Markdown 外部修改冲突和整体工程搬迁。
6. 新工程不出现地图、材料登记、旧引用字典或旧书库导入入口。
7. `formatVersion: 1` 被明确分流，不被新核误读。

默认回归不访问真实 arXiv、百度或模型服务。涉及界面布局时继续验证真实渲染、截图与交互；本模块不替代安装版验收。

## Boundaries

### Always do

- 保持工程与论文身份稳定，使用相对路径和显式 current 指针。
- 先完整提交快照／候选／revision，再原子推进 current。
- 保留不可变来源快照、失败导入现场和普通用户内容。
- 对受管写入执行基线、摘要、路径和符号链接检查。
- 用真实磁盘与真实 Electron 回归验证创建、恢复、冲突和搬迁。

### Ask first

- 修改 `formatVersion`、清单字段、保留目录或 current 提交协议。
- 删除来源快照、工程目录或无法确认归属的残留内容。
- 引入旧格式自动迁移、普通文件登记或新的受管材料类型。
- 添加依赖、远程工程服务、凭据持久化或自动后台更新。

### Never do

- 要求工程必须包含 PDF，或把 PDF 哈希当作论文身份。
- 静默覆盖 current、来源快照、用户草稿或已有工程目录。
- 因首次导入失败自动删除工程，或把导入中状态显示为正文可读。
- 恢复 `materials`、阅读地图、旧 PDF 引用字典或旧 v1 书库批量导入。
- 把普通参考文件自动提升为主论文，或根据文件名／时间猜测发布候选。
- 在工程中写入模型密钥、解析 Token 或机器专用配置。
- 另建根目录 `SPEC.md`，或在未批准后续模块规格时提前实施其能力。

## Success Criteria

- [ ] 新工程清单为 `formatVersion: 2`，只管理主论文身份和 current 指针，无 PDF、`materials` 或地图依赖。
- [ ] 首次导入的每个中断点都能区分“工程已创建”和“正文已可读”，并保留可恢复现场。
- [ ] 来源快照不可变，current 始终指向一个完整 revision；故障注入下不会出现半提交正文。
- [ ] 本地修正、来源更新和并发候选均执行基线检查，不静默覆盖用户修改。
- [ ] 普通参考文件无需登记即可存在于工程文件树，且不会获得主论文身份。
- [ ] 工程整体搬迁后身份、current、来源和 Pi 会话仍按新根目录工作。
- [ ] 外部修改、非法路径和符号链接不会被静默接受或跟随。
- [ ] 新工程不再提供旧书库导入、材料登记、地图或旧 PDF 引用字典。
- [ ] `npm run typecheck`、`npm run build` 和适用 Windows Electron 回归在实现提交上实际通过。

## Open Questions

本模块没有阻塞批准的产品开放问题。以下事项由依赖规格定义，不在本模块中提前决定：

- 文档树、revision 内容结构和重锚算法：`document-core`。
- 来源特有元数据、导入警告和恢复任务细节：`arxiv-import`、`pdf-import`。
- 工作区与阅读位置的持久化结构：`workspace`、`reader`。
- 旧 v2 工程是否迁移、只读或拒绝：`legacy-projects`。
