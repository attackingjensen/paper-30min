# 版本开发与发布约定

本约定只记录 Paper30Min 的分支和交接边界。需求探索、实施、调试和审查按已安装的 Compound Engineering 技能选择，不要求每个版本走固定的技能链。

## 版本开发

从最新 `main` 创建版本分支。同一版本可以分多次探索、形成多份 plan，由多个主对话在这条分支上串行实施。每份 plan 准备好后可先提交文档，再由实施对话接手；完成并验证一个部分后再提交。`steven123397/dev` 是 v1.2.0 的历史开发分支，不再作为长期开发入口。

没有 Issue 的小缺陷随当前实施单元修复并验证；新发现的疑难缺陷若需转交，先记录为 Issue。处理带 Issue 的缺陷时，可暂停相关开发，在 `docs/current.md` 留下阻断项和下一步；先提交已经完成且验证通过的独立改动，不为交接制造未完成的提交。修复可由主对话、子代理或新对话在当前版本分支串行完成。共享工作区的子代理交回改动和验证证据，由主对话按 `ce-work` 核对并提交；不固定要求 worktree 或额外 PR。

`docs/current.md` 是新对话的入口，简短记录当前能力、验证结果、阻断项和下一步；不记录 PR 操作流水。版本分支上的进度与 `main` 的稳定版状态可以不同，接手时先确认所在分支。

## 审查与发布

同一版本的多份 plan、修复和文档最终通过一个面向 `main` 的版本 PR 合并。合并与最终构建前完成适用的代码审查与检查，修复阻断项后复审；最终安装包在审查收敛后构建。未运行的测试或安装走查不记为通过。合并前将版本分支的 `current.md` 写成“代码已完成、待发布”等在合并后仍准确的状态。

需要 Beta 试用时，可从尚未合并的版本分支提交构建、签名并发布 `vX.Y.Z-beta.N` 预发布；后续 Beta 仍留在同一版本分支和 PR。Beta 使用独立的 `latest-beta.json`，不替换稳定版更新入口。记录试用结果后，再决定是否准备正式版。

正式版从已合并的 `main` 提交构建、签名并发布；Beta 升正式版也须重新核对版本、产物和签名。验签、远端附件及安装行为的不同证据见[签名发布经验](solutions/workflow-issues/signed-release-evidence-stages.md)。发布后直接在 `main` 提交并推送最终文档更新：`current.md` 记录实际发布状态和待办，必要时同步 `docs/releases/`；无需另开仅文档 PR。
