# 版本开发与发布约定

本约定只记录 Paper30Min 的分支、合并和发布边界。需求探索、实施、调试和审查按当前安装的 NexusKit 技能选择，不要求每个变更走固定技能链。

## 开发、审查与合并

`main` 是持续集成主干，不要求等于最新正式发布版本。日常开发从最新 `main` 创建短分支，按阶段或任务形成面向 `main` 的小 PR；不再用同一个长期分支承载整个版本的多份 plan、修复和文档。

每个增量完成并验证后再提交，提交保持原子。多份 plan 可以属于同一产品方向，但应拆成可独立审查、合并和回退的小 PR；`steven123397/dev` 与长期版本分支都属于历史工作方式，不再作为开发入口。

任务、进度和验收证据由 beads 承接，配置见 [agents/issue-tracker.md](agents/issue-tracker.md)。Linear 中的既有项目、规格和未完成票据只作历史参考，不自动迁移，也不构成当前执行顺序；后续工作按新方向重新判断。没有 Issue 的小缺陷可随当前实施单元修复，不为凑流程建票。

每个 PR 在合并前完成适用的代码审查和检查，处理阻断项后复审，并在 PR / beads 记录验证结果与未解决项。合入 `main` 只表示该增量成为当前开发基线，不代表完整版本验收或正式发布；未运行的测试、真实服务检查或安装走查不得记为通过。

## Beta 与正式版

需要 Beta 试用时，可从 `main` 的明确提交构建、签名并发布 `vX.Y.Z-beta.N` 预发布；需要稳定期时可使用短期 release branch，不恢复长期版本分支。Beta 使用独立的 `latest-beta.json`，不替换稳定版更新入口。记录试用结果后，再决定是否准备正式版。

正式版从已合入 `main` 的明确提交构建、签名并发布，Release/tag 是稳定版本的事实来源。发布前另验版本、产物、签名、安装和升级行为；CI 的类型检查、构建与开发目录测试不能替代安装版验收。发布后可直接在 `main` 提交并推送最终发布文档更新，必要时同步 `docs/releases/`，无需另开仅文档 PR。
